# 正式发布前 · 数据库业务数据清理方案

版本：v1.0（草案）
日期：2026-08-29
状态：仅设计与分析，未执行任何 DELETE / TRUNCATE / 写库操作。

重要前提：本环境无法连接 Supabase 实时库，本方案基于主项目 `/开发文件夹/docs/sql/` 下全部 21 份 Migration 文件（本库结构的权威定义）静态推导，符合「以实际记录和代码为准」的原则。执行前必须先跑「保留账号快照 SQL」以确认真实存在的管理员账号，再由你人工确认后执行。

## 0. 方案目标

清除旧用户与旧论坛业务数据，使网站进入「全新上线、无历史用户、无历史论坛内容」状态；同时完整保留数据库框架（表结构、RLS、RPC、触发器、敏感词系统、管理员权限体系、Storage 配置）。

## 4. 【保留账号清单】

清理原则：保留所有 role IN ('dev_admin','admin') 的账号，其余账号删除。

由编码历史可知，主管理员账号（dev_admin）初始化信息为：email `10281028@campus-forum.local`、UID `10281028`、role 原始值 `super_admin`（已回填为 `dev_admin`）。

保留范围（默认方案）：
- dev_admin：全部保留。
- admin：全部保留（如需仅保留单一 dev_admin，请在决策点 3 中限定具体账号）。

必须保留的原因（依赖关系）：
- get_user_role() 依据 profiles.role + account_status 判定权限；删除 dev_admin 会导致管理后台、敏感词管理 RPC、公告管理 RPC 全部失去可调用主体。
- announcements.author_id、reports.resolved_by、admin_notification_reads.admin_id 均可能指向管理员；虽无强制外键，但保留管理员可避免管理记录悬空。

执行前必须运行「保留账号快照 SQL」，拿到真实的 dev_admin/admin 的 id / uid / email / nickname 列表，并由你确认保留范围，再继续。

## 5. 外键依赖分析

auth.users 的子表（有真实外键）：
- profiles.id → auth.users(id) ON DELETE CASCADE
- comments.user_id → auth.users(id) ON DELETE CASCADE
- post_likes.user_id → auth.users(id) ON DELETE CASCADE
- post_saves.user_id → auth.users(id) ON DELETE CASCADE
- reports.reporter_id → auth.users(id) ON DELETE CASCADE
- reports.resolved_by → auth.users(id)（ON DELETE NO ACTION，无级联）

说明：删除 auth.users 会级联删除上述表的用户关联行（resolved_by 除外，故必须先清 reports）。

posts 与外键的关键结论：
- posts.id = VARCHAR，posts.user_id = VARCHAR（二者均为 VARCHAR）。
- 由 Phase3 修复文件确认，posts.user_id 是无外键的纯 VARCHAR 字段（与 auth.users 无引用约束）。
- comments.post_id、post_likes.post_id、post_saves.post_id 同样为 VARCHAR 且无对 posts 的外键。
- 结论：删除 auth.users 不会级联删除 posts；posts 及其子表必须显式删除，且依赖关系是「弱依赖」（靠 post_id 字符串关联，无数据库强制约束）。

其他外键：
- comments.parent_comment_id → comments(id) ON DELETE CASCADE（自引用，删评论时先删回复再删主评论，最稳妥）。
- admin_notification_reads.notification_id → admin_notifications(id) ON DELETE CASCADE。
- announcement_reads.announcement_id → announcements(id) ON DELETE CASCADE。
- post_images.post_id：早期文件为 UUID REFERENCES posts(id) ON DELETE CASCADE，但 posts.id 实为 VARCHAR，存在类型不一致风险；清理时对 post_images 显式 DELETE（不依赖级联）。

## 6. 触发器分析（清理过程中是否会再写数据）

逐一对全部 12 个触发器核对触发时机，结论：本项目不存在任何 DELETE 触发器，清理过程不会产生新数据。

清单与触发时机：
- on_auth_user_created —— AFTER INSERT ON auth.users（仅注册时，删除不触发）。
- trigger_profiles_updated_at —— BEFORE UPDATE（非 DELETE）。
- trigger_comments_updated_at —— BEFORE UPDATE（非 DELETE）。
- trigger_reports_updated_at —— BEFORE UPDATE（非 DELETE）。
- protect_profile_fields_trigger —— BEFORE UPDATE ON profiles（非 DELETE）。
- trg_password_reset_notify_admin —— AFTER INSERT ON password_reset_requests（非 DELETE）。
- trg_report_notify_admin —— AFTER INSERT ON reports（非 DELETE）。
- trg_announcements_updated_at —— BEFORE UPDATE（非 DELETE）。
- protect_system_message_fields_trigger —— BEFORE UPDATE（非 DELETE）。
- sv_reject_posts / sv_reject_comments / sv_reject_profiles / sv_reject_reports / sv_reject_announcements —— BEFORE INSERT OR UPDATE（非 DELETE）。
- trg_sensitive_word_hits_updated_at —— BEFORE UPDATE（非 DELETE）。
- trg_sensitive_word_hits_notify_admin —— AFTER INSERT（非 DELETE）。

风险提示：以上触发器若非 superuser（SQL Editor 默认 postgres 角色）执行 DELETE，仍可能触发 BEFORE INSERT/UPDATE 校验，但清理全部为 DELETE/无 INSERT，故不受影响。

## 7. Storage 清理方案

桶结构（保留）：
- avatars（public）—— 路径 {user_id}/{filename}。
- post-images（public）—— 路径 {post_id}/{filename}。

清理对象（清空）：
- avatars 桶内所有旧用户头像文件。
- post-images 桶内所有旧帖子图片文件。

框架资源（保留，无默认资源依赖）：
- 默认头像为外部 URL（dicebear），不存储在桶内；无框架级默认资源需保留。
- 桶本身与 Storage 策略全部保留（"Public read avatars"/"Users upload own avatar"/"Public read post images" 等）。
- 清理旧对象不影响网站框架与默认资源。

清理动作：以 postgres 角色执行 DELETE FROM storage.objects WHERE bucket_id IN ('avatars','post-images')，删除元数据后由 Supabase 垃圾回收物理文件。

## 8. 【删除顺序】

原则：先清内容/从属表（子表在前），最后清用户（父级，依赖级联干净）。

阶段 0 —— 保留账号快照（只读，需你确认）：
```sql
SELECT p.id, p.uid, p.nickname, p.role, p.account_status, u.email
FROM public.profiles p
LEFT JOIN auth.users u ON u.id = p.id
WHERE p.role IN ('dev_admin','admin')
ORDER BY p.role, p.created_at;
```

阶段 1 —— 清空内容/业务表（子表在前，全部显式 DELETE）：
```sql
DELETE FROM public.admin_notification_reads;
DELETE FROM public.admin_notifications;
DELETE FROM public.announcement_reads;
DELETE FROM public.announcements;
DELETE FROM public.system_messages;
DELETE FROM public.password_reset_requests;
DELETE FROM public.reports;
DELETE FROM public.post_images;
DELETE FROM public.post_branches;
DELETE FROM public.post_likes;
DELETE FROM public.post_saves;
DELETE FROM public.comments WHERE parent_comment_id IS NOT NULL; -- 先删回复
DELETE FROM public.comments WHERE parent_comment_id IS NULL;     -- 再删主评论
DELETE FROM public.posts;
DELETE FROM public.sensitive_word_hits; -- 清数据保留表
```

阶段 2 —— 清空用户（保留 dev_admin/admin）：
```sql
-- 安全闸门：确认存在至少一个 dev_admin，否则中止
DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM public.profiles WHERE role = 'dev_admin') THEN
    RAISE EXCEPTION '未找到 dev_admin 账号，中止清理';
  END IF;
END $$;

-- 删除非管理员 auth.users（级联清理其 profiles 及 auth 侧会话/身份）
DELETE FROM auth.users
WHERE id NOT IN (
  SELECT id FROM public.profiles WHERE role IN ('dev_admin','admin')
);

-- 防御性清理可能残留的非管理员 profile
DELETE FROM public.profiles
WHERE role NOT IN ('dev_admin','admin');
```

阶段 3 —— 清空 Storage 旧对象：
```sql
DELETE FROM storage.objects WHERE bucket_id = 'avatars';
DELETE FROM storage.objects WHERE bucket_id = 'post-images';
```

说明：全程仅 DELETE（不用 TRUNCATE），以避免误清保留表、避免依赖不确定的外键级联。auth.users 的删除需在 Supabase SQL Editor 以 postgres 角色执行（不涉及 service_role，符合项目约束）。

## 10. 【风险说明】

1. 无法连接实时库：本方案基于本地 Migration 静态推导，未实时核对线上表与真实账号。执行前必须用「保留账号快照 SQL」与下面的验证 SQL 先做只读核查。
2. posts.user_id 无外键：删 auth.users 不会级联删 posts，故 posts 必须显式删除；若漏删 posts，「全新上线」不成立。
3. reports.resolved_by 为 NO ACTION：如先删管理员会导致 FK 违反，故必须先清 reports 再删用户。
4. auth.users 直删：属 DBA 操作，Supabase Auth 侧会话/身份子表随 ON DELETE CASCADE 清理；建议在删除前备份或记录欲保留账号的 email/id，避免误删。
5. 删除后不可逆：无软删除恢复机制；建议执行前对数据库做一次快照/备份。
6. 敏感词系统不误伤：敏感词表、配置、函数、触发器均不删除，仅清 sensitive_word_hits 数据，清理后检测能力完整保留。
